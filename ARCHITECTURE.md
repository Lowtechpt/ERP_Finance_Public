# ERP Finance — System Architecture

> A full-stack financial operations dashboard for PRIMAVERA ERP data, built to run in three
> different postures — connected to a real SQL Server ERP, offline against a portable SQLite
> demo, or fully static on GitHub Pages — without branching the frontend code.

## 1. System Overview

### 1.1 High-Level Diagram

```
┌──────────────────────────────────────────────────────────────────────┐
│                              BROWSER                                  │
│  React 19 SPA (hash router) · 23 pages · Vite dev server / static      │
│  bundle · lazy-loaded route chunks · localStorage for AI key slots     │
└───────────────────────────────┬────────────────────────────────────┘
                                 │ fetch("/api/...")  (dev: Vite proxy)
                                 ▼
┌──────────────────────────────────────────────────────────────────────┐
│                    server/primavera-api.ts (Node http)                │
│  Rate limiting → CORS/CSP headers → input validation → route table    │
│  30 endpoints, dispatched to ONE of two interchangeable backends:      │
└───────────┬───────────────────────────────────────────┬──────────────┘
            │ PRIMAVERA_MODE=sqlserver                   │ PRIMAVERA_MODE=demo (default)
            ▼                                             ▼
 ┌────────────────────────────┐              ┌──────────────────────────────┐
 │  server/backends/           │              │  server/backends/demo.ts      │
 │  sqlserver.ts                │              │  → server/db/sqlite-client.ts │
 │  spawns `sqlcmd`, parses CSV/│              │  reads a pre-seeded, read-only│
 │  JSON, CP850→UTF-8 repair    │              │  SQLite file (node:sqlite)    │
 └──────────────┬───────────────┘              └──────────────┬────────────────┘
                ▼                                              ▼
     PRIMAVERA Evolution v10                     erp-finance-demo.sqlite
     SQL Server "PRIDEMO"                        (generated by build-demo-db.ts
     (Clientes, CabecDoc, Movimentos,              from seed-data.ts, ~thousands
      Funcionarios, GPR_OrdemFabrico...)           of synthetic-but-realistic rows)
```

A third mode — **static** — removes the backend entirely: `npm run build:static`
pre-renders every endpoint's JSON response to a file under `dist/api-static/`, and the
frontend fetches those files directly instead of hitting `/api/*`. This is what runs on
GitHub Pages (`ERP_Finance_Public`), since Pages cannot host a Node process.

### 1.2 Components

| Layer | Technology | Responsibility |
|---|---|---|
| Frontend | React 19 + TypeScript + Vite 8 | Routing, rendering, client-side filtering/search, AI chat UI |
| Backend | Node.js `http` module (no framework) | Auth-free JSON API, rate limiting, input validation, security headers |
| Data access | `sqlserver.ts` / `demo.ts` (same interface) | Abstracts *where* data comes from behind one function contract |
| Database (prod) | SQL Server 2022 (PRIMAVERA Evolution schema) | System of record — Clientes, CabecDoc, Movimentos, Funcionarios, etc. |
| Database (demo) | SQLite via Node's built-in `node:sqlite` | Zero-dependency, file-based, read-only snapshot for offline/public use |
| AI | Google Gemini (`gemini-2.0-flash-lite` default) | Financial summaries, root-cause narratives, chat — called from the browser with a user-supplied key, and from the backend for the context-aware `/api/ai/chat` endpoint |

### 1.3 Data Flow (Live Mode)

```
Page mounts → useEffect fires fetch(apiUrl("/api/cashflow"))
  → Vite dev proxy rewrites /api/* → http://127.0.0.1:5000 (vite.config.ts)
  → primavera-api.ts: rate-limit check → CORS/CSP headers → route match
  → backend.getCashFlow() (sqlserver.ts or demo.ts, same signature)
  → sqlserver.ts: spawns `sqlcmd -f 65001 -Q "<query>"`, decodes CP850 if needed,
    parses tabular output into typed rows
  → JSON response with {source, server, database, generatedAt, ...data}
  → page state updates → formatCurrency/formatDate/formatPercent (src/lib/format.ts)
  → KPIGrid / DataTable / charts render
```

Every backend response carries a `source` field (`"primavera-sql"` vs `"demo-sqlite"`) so the
UI can label data provenance instead of pretending the demo data is real — a deliberate
honesty choice for a portfolio project a hiring manager might poke at.

### 1.4 Deployment Topology

```
Local dev:      concurrently → [npm run dev:api → tsc -p tsconfig.server.json && node dist-server/primavera-api.js]
                                [vite --host 127.0.0.1]
                                port 5000 (API)                  port 5173 (proxies /api)

Docker:         docker compose up --build → single "app" container (target: demo)
                installs no node_modules at runtime (API has zero runtime deps),
                serves built frontend (dist/) + API from port 5000, SQLite baked
                into the image at build time. A "dev" compose profile (target:
                development) adds Vite HMR on 5173 against the same backend.

Public demo:    GitHub Actions (deploy-pages.yml) builds `--mode static`,
                generates static JSON snapshots, publishes dist/ to GitHub Pages
                → https://lowtechpt.github.io/ERP_Finance_Public/  (no backend at all)
```

The API server binds to `MEG_FINANCE_API_HOST` (default `127.0.0.1`; containers
set `0.0.0.0`). When `STATIC_DIR` is set, the same Node process also serves the
built frontend with an SPA fallback and path-traversal protection, so the
Docker demo runs as one container on one port.

## 2. Frontend Architecture

### 2.1 Scale

- **23 dedicated pages** under `src/pages/*.tsx` (Dashboard, CashFlow, Payables, Banks, DRE,
  Profitability, BreakEven, ComparePeriods, BudgetVsActual, CollectionsComms,
  ExecutiveSummary, RootCauseAnalysis, CreditRisk, Alerts, AlertThresholds, HR,
  CostAllocation, LiquidityPage, LiquidityRisk, CashFlowForecast, RiskConcentration,
  IndustrialCosts, ProductionPage).
- **30+ routes** in total once the generic `ModulePage` router is counted — it renders any
  PRIMAVERA module (`#vnd`, `#cmp`, `#inv`, `#crm`, `#gpr`, `#bas`, `#erp`, `#eap`, `#fil`,
  `#tte`, `#webapi`, `#epk`, `#int`, `#mob`, `#pcm`, `#stp`, `#prj`, `#cct`, `#tes`, `#cbl`)
  from a single `moduleViews` lookup table instead of one file per module.
- Routing is a **hash router built by hand** (`getCurrentRoute()` reads
  `window.location.hash`), not React Router — deliberate, see §7.

### 2.2 Component Hierarchy

```
App()                                    src/App.tsx — router, nav, receivables view; lazy-loads every page
├── AppNav / MobileNav                   mega-menu (desktop) + Sheet/Accordion (mobile)
├── <route dispatch>
│   ├── PageWrapper                      src/components/PageWrapper.tsx — gradient shell, memo()
│   │   ├── SectionHeader                category / title / description
│   │   ├── KPIGrid                      5-col responsive metric grid
│   │   ├── DataTable<T>                 generic sortable table (ColumnDef<T>[])
│   │   ├── PageLoadingState / PageEmptyState
│   │   └── page-specific charts/cards
│   ├── ModulePage                       generic PRIMAVERA module renderer (30+ routes)
│   └── AiWorkspace / GeminiChatPanel    lazy-loaded, Gemini chat + inline charts
```

Every one of the 23 dedicated pages follows the same composition:

```tsx
export default function CashFlowPage() {
  const [data, setData] = useState<CashFlowData | null>(null);
  useEffect(() => {
    let ignore = false;
    fetch(apiUrl("/api/cashflow"))
      .then((r) => r.json())
      .then((d) => !ignore && setData(d))
      .catch(() => !ignore && setError(...));
    return () => { ignore = true; };
  }, []);

  if (!data) return <PageLoadingState />;
  return (
    <PageWrapper>
      <SectionHeader title="Fluxo de caixa" description="..." />
      <KPIGrid items={[...]} />
      <DataTable columns={columns} data={data.rows} />
    </PageWrapper>
  );
}
```

The `ignore` flag pattern guards every fetch effect against setting state after unmount —
applied consistently across all 23 pages (visible in `App.tsx` for the receivables/customers/
modules fetches, and replicated per-page).

### 2.3 State Management

No Redux, Zustand, or Context-heavy state layer. Deliberately:

- **Local `useState`** per page for fetched data, loading, and error state.
- **`useMemo`** for derived/filtered views (`baseReceivables`, `receivables`, `filterCounts`
  in `App.tsx`) so filtering 8+ receivable rows against search + status filters doesn't
  re-run on every unrelated re-render.
- **`useCallback`** for event handlers passed into memoized children (`notify`,
  `handleSelectFilter`, `handleClearFilters`).
- **`localStorage`** for the one piece of state that must survive reloads and isn't
  server data: Gemini API key slots and the active model (`GeminiChatPanel`).
- Route state (`currentRoute`) is derived from `window.location.hash` via a
  `hashchange` listener — the URL *is* the state, no separate router state to desync.

### 2.4 Data Fetching Strategy

`src/lib/api.ts` exports two primitives used everywhere instead of a fetch wrapper library:

```ts
export const isStatic = import.meta.env.MODE === "static";
export function apiUrl(path: string): string {
  return isStatic ? `${import.meta.env.BASE_URL}api-static${path}.json` : path;
}
```

This one function is what lets 23 pages share identical `fetch(apiUrl("/api/x"))` code across
three deployment modes (live backend, Docker, static GitHub Pages) — the pages never know
which mode they're in. Error handling is uniform: `response.ok` check → typed `.json()` →
`catch` sets a page-local error string, rendered instead of the data view. There is no
client-side cache/staleness layer (no React Query/SWR) — each page fetches once on mount,
consistent with the "always show current PRIMAVERA data" priority over perceived speed.

### 2.5 Code Splitting

All 23 pages plus `AiWorkspace` and `GeminiChatPanel` are `lazy()`-loaded from `App.tsx`:

```tsx
const CashFlowPage = lazy(() => import("@/pages/CashFlowPage"));
...
<Suspense fallback={<PageLoadingState message="A carregar página..." />}>
  {isCashFlowRoute ? <CashFlowPage /> : ...}
</Suspense>
```

Only the route the user actually opens downloads its chunk — a Dashboard visit never pulls
in the HR analytics or Production cost-allocation bundles. Combined with Vite's default
vendor chunking, the production bundle for the initial route is **332 KB (102 KB
gzipped)** as of the last `npm run build`. `vite.config.ts`
also wires in `rollup-plugin-visualizer`, generating `dist/stats.html` on every non-static
build so bundle regressions are visible without extra tooling.

### 2.6 Design System (frontend half — see §5 for the full picture)

Reusable primitives live in `src/components/`: `PageWrapper`, `SectionHeader`, `KPIGrid`,
`DataTable<T>`, `PageLoadingState`, `PageEmptyState`, `metrics.tsx` (`StatusBadge`,
`Activity`). Lower-level UI primitives (`Button`, `Input`, `Accordion`, `Sheet`,
`NavigationMenu`, `grid-card`, `grid-pattern`) live in `src/components/ui/`, following the
shadcn/ui convention: copied into the repo (not an npm dependency), built on Radix UI
primitives (`@radix-ui/react-accordion`, `-dialog`, `-navigation-menu`, `-slot`) with
`class-variance-authority` for variant props and `tailwind-merge`/`clsx` for class
composition (`cn()` helper).

## 3. Backend Architecture

### 3.1 Why No Express

`server/primavera-api.ts` is a single `http.createServer(handler)` — no Express, Fastify, or
Koa. The `handler` function is a long chain of `if (request.url === "/api/x")` checks,
Express-style in spirit but with zero framework dependency:

```ts
export const handler: (request: IncomingMessage, response: ServerResponse) => Promise<void> =
  async (request, response) => {
    if (!checkRateLimit(clientIp)) { /* 429 */ return; }
    if (contentLength > MAX_REQUEST_SIZE) { /* 413 */ return; }
    if (request.method === "OPTIONS") { /* preflight */ return; }
    try {
      if (request.url === "/api/health") { ... return; }
      if (request.url === "/api/receivables") { ... return; }
      // ...28 more routes (30 total)
      sendJson(response, 404, { error: "Not found" }, origin);
    } catch (error) { /* 500, sanitized in production */ }
  };
```

This keeps the deploy surface to "one Node process, zero npm-installed HTTP framework" —
relevant given the app also needs to run unmodified inside `demo`/`sqlserver`/Docker/CI
contexts. The trade-off (route table readability past 30 endpoints) is accepted; see §7.

**Compiled, not run directly.** `server/**/*.ts` is the source of truth, type-checked
under `strict` + `noUnusedLocals` + `noUnusedParameters`. `npm run build:server` runs
`tsc -p tsconfig.server.json`, emitting plain JS to `dist-server/`; the server then runs
as `node dist-server/primavera-api.js` — no `ts-node`/`tsx` in production. The previous
parallel `.mjs` implementation of the API is gone; TypeScript is the only source.

**Zero runtime dependencies.** The compiled API imports only Node built-ins —
`node:http`, `node:path`, `node:fs/promises`, `node:url`, `node:sqlite`,
`node:child_process` — nothing from `node_modules` at runtime. That's why the
production Docker image (§6.2) can skip `npm install` entirely in its final stage.

### 3.3 Middleware Stack (hand-rolled, applied in order per-request)

1. **Rate limiting** — in-memory `Map<ip, {count, resetTime}>`, 100 req/min per IP, 429 on
   breach, swept every 5 minutes via `setInterval`.
2. **Request size guard** — rejects any request with `Content-Length` over 100 KB (413).
3. **Content-Type enforcement** — POST requests must declare `application/json` (415
   otherwise).
4. **CORS preflight (OPTIONS)** — short-circuits with the security headers and a 204,
   without hitting rate limiting logic twice.
5. **Route dispatch** inside a top-level `try/catch` — one exception handler for the whole
   route table, so no single endpoint can crash the process without a JSON 500 response.

### 3.4 Database Abstraction

Both backends export the *same* async function surface (`getReceivables`, `getDashboard`,
`getCashFlow`, `getDRE`, `getHRCosts`, `getTopProducts`, `buildFinancialSummary`, ...), so
`primavera-api.ts` never branches on mode past the single line that selects which module to
import:

```ts
const PRIMAVERA_MODE: "sqlserver" | "demo" =
  process.env.PRIMAVERA_MODE === "sqlserver" ? "sqlserver" : "demo";
const backend = PRIMAVERA_MODE === "sqlserver" ? sqlServerBackend : demoBackend;
```

- **`server/backends/sqlserver.ts`** — shells out to `sqlcmd`, decodes CP850-encoded
  output when the ERP returns Windows-1252/CP850 bytes for accented Portuguese names (a
  real bug hit and fixed during development — see `decodeCp850()`/`decodeSqlcmdBuffer()`),
  and parses `sqlcmd`'s tabular stdout into typed JSON via `parseSqlJson()`.
- **`server/backends/demo.ts`** — delegates to `server/db/sqlite-client.ts`, a 22-line
  wrapper around Node's built-in `node:sqlite` (`DatabaseSync`, opened `readOnly: true`)
  with two functions, `all()` and `get()`, both parameterized (no string-built SQL).
- **`server/db/build-demo-db.ts`** — one-time seed script: reads `server/db/schema.sql`,
  creates `erp-finance-demo.sqlite`, and populates it from `seed-data.ts`'s synthetic
  generators (`randInt`, `randFloat`, `pick`) — realistic-shaped but entirely fake data,
  regenerated with `npm run seed:demo`.

### 3.5 Error Handling Strategy

Two-tier, environment-aware:

```ts
} catch (error) {
  if (NODE_ENV === "production") {
    sendJson(response, 500, { error: "Request failed. Please try again." }, origin);
  } else {
    sendJson(response, 500, { error: "Request failed", message: String(error) }, origin);
  }
}
```

`sendJson()` also strips `detail` fields and truncates `message` to 255 chars on any 4xx/5xx
response when `NODE_ENV === "production"`, so stack traces and internal error text never
reach a client outside development. This is applied uniformly, not per-endpoint.

### 3.6 Security Measures (summary — full detail in `SECURITY_AUDIT.md`)

- Input sanitization (`sanitizeString`, `validateLimit`, `validateMetric`, `validateOrder`)
  on every query-string-driven endpoint.
- CORS allow-list (`ALLOWED_ORIGINS` env var, defaults to the two local dev origins).
- Security headers on every response: `X-Content-Type-Options`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, a restrictive `Content-Security-Policy`, and `Strict-Transport-Security`
  when `NODE_ENV=production`.
- Rate limiting (100 req/min/IP) and request-size caps (100 KB) as described above.

### 3.7 Demo Backend Design — Static vs Dynamic

The demo backend has **two personalities**:

1. **Dynamic** (`npm run dev` with `PRIMAVERA_MODE=demo`, the default): the Node server
   answers `/api/*` in real time by querying the SQLite file — same request/response shape
   as `sqlserver.ts`, so the frontend can't tell the difference.
2. **Static** (`npm run build:static`): `server/db/generate-static-snapshots.ts` calls
   every backend function once at build time and writes each result to
   `dist/api-static/<endpoint>.json`. `apiUrl()` (§2.4) then points the frontend at those
   files instead of a live server. This is the only way to make a full financial dashboard
   work on GitHub Pages, which serves static files exclusively.

## 4. Database Design

### 4.1 Two Schemas, One Contract

- **Production**: the real PRIMAVERA Evolution v10 schema (SQL Server, database
  `PRIDEMO`) — not owned by this project, queried read-mostly. Key tables: `Clientes`,
  `Fornecedores`, `Artigo`, `CabecDoc` / `LinhasDoc` (sales & purchase documents),
  `Movimentos` (accounting entries, Classe 64 = payroll costs), `Funcionarios`,
  `FuncRecibos` / `FuncRecibosProcs` (payroll), `RHP_Ferias` (vacation),
  `RHP_HistoricoRegistoVinculo`, `GPR_OrdemFabrico` (manufacturing orders).
- **Demo**: `server/db/schema.sql` defines a SQLite mirror of the ~20 entities the app
  actually reads (`Cliente`, `Fornecedor`, `Armazem`, `CabecDocRecord`,
  `CabecComprasRecord`, `CabecTesourariaRecord`, `ContaBancaria`, `Contacto`, and the HR
  tables), seeded by `seed-data.ts` with parameterized random generators so row counts and
  distributions are adjustable without hand-editing fixtures.
- **No ORM, no migrations.** An earlier TypeORM + `mssql` experiment
  (`src/database/data-source.ts`, entity/migration files under `src/database/`) was
  removed entirely — it was declared in `package.json` but never actually wired into the
  running app, and it broke `npm run build` with type errors. There is currently no
  migration-managed schema anywhere in this project: the demo database is fully
  regenerated from `schema.sql` + `seed-data.ts`, and the production schema is PRIMAVERA's
  own, owned and migrated outside this codebase.

### 4.2 Design Patterns

- **Fact vs. dimension, informally**: transactional tables (`CabecDoc`, `Movimentos`,
  `LinhasDoc`) are joined against relatively static reference tables (`Clientes`,
  `Fornecedores`, `Artigo`) inside the SQL run by `sqlserver.ts` — the app doesn't
  materialize its own star schema, it queries PRIMAVERA's OLTP schema directly and shapes
  the result in JS (`buildFinancialSummary()`, per-endpoint aggregation functions).
- **Read-only by construction**: the SQLite demo client opens with `{ readOnly: true }` —
  the demo can never be corrupted by a stray write bug, and `/api/register-payment` in demo
  mode is a no-op acknowledgement rather than a real mutation.
- **Metadata envelope**: every backend response spreads `backend.meta`
  (`{source, server, database}`) plus a fresh `generatedAt` timestamp, so API consumers
  (and a reviewer inspecting Network tab) always know which backend answered and when.
- **Soft provenance instead of soft delete**: PRIMAVERA's own tables use status columns
  (e.g., `CabecDocStatus`) which the app reads (`row[8]` states like "Vencido"/"Pendente"/
  "Parcial" in `App.tsx`) rather than reimplementing status logic client-side.

### 4.3 Indexing Strategy

Production indexing is inherited from the PRIMAVERA Evolution schema (out of this
project's control). On the SQLite demo side, `schema.sql` is deliberately small
(thousands, not millions, of rows) so no additional indexes were needed for the query
patterns exercised by the 30 endpoints — a documented non-goal rather than an oversight,
since the demo's job is to *look* real, not scale.

### 4.4 Data Integrity

- Parameterized queries only on the SQLite path (`all(sql, params)` / `get(sql, params)`
  in `sqlite-client.ts`) — no string concatenation into SQL.
- The SQL Server path shells out to `sqlcmd`, which is why every query-string parameter
  that reaches a query (`limit`, `metric`, `order`, `meses`, `doc`) is validated with an
  allow-list regex or numeric cap *before* it can influence the constructed SQL text —
  see §3.2 and `SECURITY_AUDIT.md` §1.
- Encoding integrity: `runSql()` forces `sqlcmd -f 65001` (UTF-8) and falls back to an
  internal CP850 decoder when the ERP still returns legacy-encoded bytes, fixing garbled
  Portuguese names (`Luís`, `Valença`, `Araújo`) at the source instead of patching them in
  the UI.

## 5. Design System

### 5.1 Component Library (7 components in `src/components/`, plus `ui/` and `ai/` subdirectories)

| Category | Components |
|---|---|
| Layout | `PageWrapper`, `SectionHeader`, `ModulePage` |
| Data display | `KPIGrid`/`KPIItem`, `DataTable<T>`/`ColumnDef<T>`, `metrics.tsx` (`StatusBadge`, `Activity`) |
| Feedback | `PageLoadingState`, `PageEmptyState` |
| Primitives (`ui/`) | `Button`/`buttonVariants` (CVA), `Input`, `Accordion`/`AccordionItem`/`AccordionTrigger`/`AccordionContent`, `Sheet`/`SheetContent`/`SheetTrigger`/`SheetClose`, `NavigationMenu` family, `grid-card`, `grid-pattern` |
| AI | `AiWorkspace`, `GeminiChatPanel`, `AiInlineCharts`, `CashflowInsight`, `CollectionsInsight`, `PersonnelInsight` |

Every layout primitive is wrapped in `memo()` — `PageWrapper` and `KPIGrid` are pure
presentational components re-rendered on every page mount, so memoizing them avoids
needless diff work when a parent's unrelated state (e.g., a `useState` toast) changes.

### 5.2 The One Page Pattern

```tsx
<PageWrapper>                          {/* gradient shell, min-h-screen, consistent padding */}
  <SectionHeader title="..." description="..." />
  <KPIGrid items={[{ label, value, tone }]} />
  <DataTable columns={columns} data={rows} />
  {loading && <PageLoadingState />}
  {data.length === 0 && <PageEmptyState />}
</PageWrapper>
```

This exact shape repeats across all 23 dedicated pages. A later token sweep replaced raw
Tailwind palette classes with the semantic tokens throughout — `border-slate-200` →
`border-border`, `bg-slate-50`/`white` → `bg-muted`/`bg-background`, `rounded-2xl`/`3xl` →
`rounded-lg`/`xl` — so the hand-built receivables view (`App.tsx`) and the 23 dedicated
pages read as one system instead of two competing visual languages.

### 5.3 Styling Approach

Tailwind CSS v4 (`@tailwindcss/vite` plugin, no separate PostCSS config needed) with a
small custom layer in `src/styles.css` (148 lines) for tokens Tailwind's defaults don't
cover: `bg-page` (the app-wide off-white background), `text-danger`/`text-success` tone
aliases, and `card-elevated` (a soft shadow used by `KPIGrid`). Component variants use
`class-variance-authority`; conditional/merged class strings use the `cn()` helper
(`clsx` + `tailwind-merge`) everywhere instead of manual string concatenation.

### 5.4 Color Palette & Typography

- **Semantic tokens, not raw Tailwind colors.** `src/styles.css` defines the palette once
  under `@theme inline` (`--color-background`, `--color-muted`, `--color-border`,
  `--color-primary`, plus `-soft` variants for `danger`/`warning`/`success`/`info`), and
  every page consumes `border-border`, `bg-muted`, `text-danger`, etc. instead of
  `slate-200`/`emerald-600`/`rose-600` literals. A later sweep removed the raw palette
  classes that had crept into all 23 pages, so the same visual change (say, deepening the
  danger red) now happens in one file instead of 400+ call sites.
- **Semantic tones** (`KPIGrid`'s `toneClasses`): `default` → `text-foreground`, `success`
  → `text-success`, `danger` → `text-danger`, `warning` → `text-warning`, `info` →
  `text-info`. Colour is reserved for values that mean something (overdue, over budget,
  above target) — KPIs default to neutral rather than being colour-coded decoratively.
- **Sidebar** uses its own token set (`--color-sidebar*`): a light surface with a hairline
  border, separate from the page tokens, so it reads as chrome rather than another panel.
- **Numbers are `tabular-nums`** everywhere a KPI or table cell renders currency/percent,
  so columns of numbers align — a detail that shows in screenshots more than it sounds.

### 5.5 Responsive Design Strategy

`KPIGrid`: `grid-template-columns: repeat(auto-fit, minmax(190px, 1fr))` — a fluid grid
that creates as many columns as fit the viewport, rather than switching between fixed
breakpoints. The same pattern (`.grid-fluid` in `styles.css`) is reused by `ModulePage`'s
stat rows. Navigation: `AppSidebar` (a collapsible left rail, `hidden lg:flex`) vs.
`MobileNav` (a Radix `Sheet` + accordion, opened from a header button below `lg`) — two
renderings of the *same* `navSections` data, not two maintained menus. Tables
(`DataTable`, the receivables grid in `App.tsx`) wrap in `overflow-x-auto` with a
`min-w-[...]` floor so dense financial tables scroll horizontally on narrow viewports
instead of collapsing unreadably.

### 5.6 Accessibility Considerations

- Radix UI primitives (`Dialog`, `Accordion`, `NavigationMenu`) provide keyboard
  navigation, focus trapping, and ARIA roles out of the box rather than reimplemented.
- Interactive icon-only buttons carry explicit `aria-label` (`"Abrir menu"`, `"Fechar
  menu"`, `"Fechar detalhe"`, `"Selecionar {cliente}"` in `App.tsx`).
- Checkboxes in the receivables table are labelled per-row (`aria-label={`Selecionar
  ${row[2]}`}`) rather than relying on visual position alone.
- **Known gap** (honestly, not glossed over): no automated accessibility test (axe-core /
  Playwright a11y assertions) runs in CI yet. Accessibility has been checked manually
  (keyboard navigation, screen-reader labels) but not verified by tooling.

## 6. Deployment Architecture

### 6.1 Development

```bash
npm run dev
# = concurrently -k -n api,vite "npm run dev:api" "vite --host 127.0.0.1"
# dev:api = npm run build:server && node dist-server/primavera-api.js
```

Two processes, one command: the API on `127.0.0.1:5000`, Vite on `127.0.0.1:5173` with
`/api` proxied to the backend (`vite.config.ts`'s `server.proxy`). `-k` (kill-others) means
either process dying takes the other down with it, avoiding orphan processes that hold the
API port open after a crash.

### 6.2 Staging / Self-Hosted (Docker)

```bash
docker compose up --build
```

`Dockerfile` is a three-stage build (`builder` → `demo` → `development`, Node 22 Alpine):
the `builder` stage runs `npm ci`, then `npm run build && npm run seed:demo` (compiling
frontend + backend and baking the SQLite demo database into the image at build time); the
`demo` stage copies only `dist/`, `dist-server/`, and the SQLite file from the builder —
**no `npm install` at all**, since the compiled API has zero runtime dependencies — and
runs `node dist-server/primavera-api.js` as the non-root `node` user on port 5000, serving
both the API and the built frontend (`STATIC_DIR=/app/dist`). `docker-compose.yml` wires a
health check against `/api/health` and sets `ALLOWED_ORIGINS` for the containerized
network. A `dev` compose profile (`docker compose --profile dev up --build`, target:
`development`) adds Vite HMR on port 5173 against the same backend, with `src/` and
`server/` bind-mounted for live editing.

### 6.3 Production (GitHub Pages, static)

```bash
npm run build:static
# = tsc -b && vite build --mode static && node dist-server/db/generate-static-snapshots.js
```

`vite.config.ts` detects `mode === "static"` and, when `GITHUB_REPOSITORY` is set (i.e.,
running inside GitHub Actions), rewrites the Vite `base` to `/${repoName}/` — required
because GitHub Pages serves project sites from a subpath, not the domain root.
`generate-static-snapshots.ts` then calls every backend function once and freezes the
output as JSON files the frontend can `fetch()` with no server at all.

### 6.4 CI/CD Pipeline

`.github/workflows/ci.yml` runs on every PR and push to `main`:

1. Checkout, Node 22 with npm cache (`node:sqlite`, used by the demo backend, needs
   Node ≥22.5).
2. `npm ci`.
3. `npm run typecheck` (`tsc -b --pretty`, strict mode).
4. `npm run build` (frontend + backend compile).
5. `npm run test` — Jest unit tests with coverage.
6. `npm run test:node` — Node's built-in test runner against the compiled demo backend
   (`server/backends/demo.test.mjs`).
7. Upload the coverage directory as a build artifact.

There is **no database service container, no migration step, and no Codecov upload** —
an earlier version of this workflow attempted all three against a TypeORM setup that
never actually compiled; that workflow could never have passed and has been replaced
with the pipeline above. E2E tests (Playwright) are configured in the repo but are
**not** run in CI.

`.github/workflows/deploy-pages.yml` is the separate publish pipeline: builds in static
mode and deploys `dist/` to GitHub Pages on push to the public branch.

### 6.5 Database Strategy (No Migrations)

There is no ORM and no migration tooling in this project. The SQLite demo database is
fully regenerated from `server/db/schema.sql` + `server/db/seed-data.ts` on every
`npm run seed:demo` — simpler and correct for a read-only, disposable dataset. The
production SQL Server schema belongs to PRIMAVERA and is managed entirely outside this
codebase; the app only reads it via `sqlcmd`. A prior TypeORM-based migration track
(§4.1) was removed because it was never actually integrated and broke the build.

## 7. Key Design Decisions

### 7.1 Why React + TypeScript

Strict-mode TypeScript (`tsconfig.json` project references: `app`, `node`, `server`) across
*both* frontend and backend catches shape mismatches between what an endpoint returns and
what a page expects at compile time — relevant here because the API's shape is dictated by
whatever PRIMAVERA's SQL Server schema happens to name a column (`OutrosCustosPrevito` is a
real, misspelled column name in the ERP that has to be matched exactly — see its use in
`server/backends/sqlserver.ts`). Typing the boundary once, in both directions,
turns "the ERP's schema doesn't match my assumption" from a runtime `undefined` into a
build failure.

### 7.2 Why Dual Backends (SQL Server + SQLite)

The project has two audiences with incompatible constraints: a real deployment against a
company's PRIMAVERA instance (which nobody outside that network can reach), and a public
portfolio demo anyone can run or visit. Rather than fork the frontend or maintain two
codebases, `sqlserver.ts` and `demo.ts` implement the *identical* async function contract,
selected by one environment variable (`PRIMAVERA_MODE`). The alternative — mocking data in
the frontend — was rejected because it would leave 23 pages untested against a real backend
contract; instead, the "mock" is a second real backend with a real (if synthetic) database
behind it.

### 7.3 Why SQLite for the Demo

`node:sqlite` (Node's built-in module, no `better-sqlite3` native binary to compile) means
`npm ci` alone gets a stranger's machine running the demo — no Docker, no external SQL
Server install, no `sqlcmd` on `PATH`. Opening the file `readOnly: true` also means the
"reset the demo" operation is `git checkout -- server/db/erp-finance-demo.sqlite` or
`npm run seed:demo`, not a database-admin task.

### 7.4 Why GitHub Pages for the Public Demo

Zero-cost static hosting with a CDN and HTTPS by default, and the "static snapshot" build
mode (§6.3) turns the constraint (no server allowed) into the same code path already
exercised by the dynamic demo backend — `generate-static-snapshots.ts` reuses `demo.ts`'s
functions verbatim rather than hand-authoring fixture JSON. The trade-off: `/api/document-
lines`, `/api/register-payment`, and `/api/open-erp` are inherently dynamic and are
explicitly disabled/no-op'd in static mode (`isStatic` checks in `App.tsx`), with a message
telling the visitor why, instead of a silent failure.

### 7.5 Why Custom Components Instead of a Component Framework

shadcn/ui's model — copy Radix-based primitives into the repo instead of `npm install`-ing
a component library — was chosen so the components in `src/components/` (7 top-level
files, plus the Radix-based primitives in `ui/` and the AI-specific components in `ai/`)
compile to exactly the Tailwind classes the app uses, with no unused variant code shipped
and no version-lock risk on a UI library's breaking changes. The cost (components are code
the project owns and must maintain) was accepted deliberately for a project whose whole
premise is showing ownership of the stack, not integration skill with a third-party kit.

### 7.6 Performance vs. Maintainability Trade-offs

- **No client-side data cache (React Query/SWR)**: simpler mental model, one fewer
  dependency, at the cost of re-fetching on every route revisit. Accepted because
  PRIMAVERA data changes throughout the business day — a stale cache would be a correctness
  bug, not just a UX nuance, for a financial dashboard.
  Custom in-memory rate limiting (`Map`) instead of Redis: correct for a single-process
  Node server and zero extra infra, but would need to move to a shared store the moment the
  API runs behind more than one instance — documented as a known scaling boundary, not
  hidden.
- **`sqlcmd` subprocess instead of a native SQL Server driver** for the production path:
  slower per-query (process spawn overhead) than a TDS driver would be, but was the
  fastest way to get Windows-authenticated access to a locked-down `PRIDEMO` instance
  without managing SQL Server credentials in the app. This remains a real, stated risk
  surface (see `SECURITY_AUDIT.md` §1) rather than a solved problem — an earlier attempt
  to replace it with a parameterized `mssql`/TypeORM driver was removed (§4.1) because it
  was never actually wired into the running app and broke the build; migrating the
  `sqlcmd` path to a real parameterized driver remains open future work.
